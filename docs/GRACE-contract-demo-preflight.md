# GRACE: отдельный демонстрационный стенд ESEPTEP

Подготовка, не инструкция для немедленного запуска на действующем сервере. Команды с заменяемыми путями выполняет администратор после согласования конкретного VPS, имени и режима доступа. Не использовать данные клиентов, копию боевой базы или настройки действующих сайтов.

## До любых изменений

1. Подтвердить точный VPS и отдельное имя для демо. Не выбирать сервер по одному названию Grace. Установить, чей DNS, кто утверждает доступ и как проверяются действующие сайты до и после выкладки.
2. Администратор отдельно проверяет ресурсы и конфликты командой `free -m; df -h; ss -lnt`. Без права чтения чужих конфигураций не исследовать содержимое действующих проектов. Сопоставить доступные ресурсы с замером репетиции, заранее согласовать лимит и число тестовых пользователей.
3. Поставить только точный принятый Git SHA в новую директорию релиза под отдельным системным пользователем. Свои venv, секрет, лог, loopback-сокет/порт, база и каталог приватных файлов. При использовании штатной SQLite держать базу на локальном диске; начать с одного рабочего процесса и измерить конкуренцию, а не переключать СУБД одновременно с показом. Исключить совместное использование каталога или базы с production.
4. **Закрытый режим:** включать только для отдельного приложения: `ESEPTEP_CLOSED_PILOT=1` с `DJANGO_ENV=production`, HTTPS, одним точным hostname/CSRF origin, собственной закрытой базой и приватным каталогом. Пример: `ops/closed-pilot.env.example`. `ESEPTEP_DEMO_MODE=1` и синтетические ответы в этом режиме запрещены. Без отдельного opt-in обычный production не меняется.
5. Вход только по выданным оператором учётным данным. После входа участие проверяется везде по группе Django `ESEPTEP closed pilot`; одна учётная запись без группы не даёт доступа. Саморегистрация и учебные примеры недоступны. Допуск проекта «Мой ремонт» по городу/проекту остаётся отдельным. Выдавать тестовые аккаунты раздельно; проверить скрытие проекта, оригинала и скачивания для другого пользователя. Публикуются только `collectstatic` и приложение через проверку прав; не выдавать приватные каталоги через nginx, отдельные media URL или индекс каталога. Не журналировать тело запроса, документы и токены.

## Запуск после согласования

- Собственное WSGI-окружение с зафиксированными зависимостями. Использовать `config.wsgi:application` за отдельной службой; bind только на согласованный loopback либо собственный Unix-сокет. Не использовать Django runserver на сетевом адресе. Подтвердить версии Python и WSGI-сервера по файлам принятого выпуска.
- Перед первым запуском проверять `python manage.py check --deploy`, `python manage.py migrate --plan`, затем мигрировать **только новую/проверенную демобазу** и выполнить `python manage.py collectstatic --noinput` в каталоге релиза. Восстановление базы и приватных файлов испытать в отдельной директории до перевода ссылки.
- Собственный HTTPS virtual host на согласованном имени, без переноса портов действующих приложений. Сначала проверить внутренний upstream и отдельный хост; после `nginx -t` согласованный reload вместо restart. Существующий портал проверить до и после по согласованным страницам.
- ИИ по умолчанию выключен. Для разрешённых пилотных запросов подтвердить текущий общий остаток $10 на анализ плана и договора. Не копировать старый ключ между машинами и не поднимать независимые счётчики. Пока локальный и серверный стенды не имеют согласованного единого бюджета, платный ИИ может быть включён только на одном из них. Перенос состояния бюджета должен исключать двойные траты и не увеличивать лимит. При выключенном ИИ шаблоны, редактура и скачивание работают.
- Проверка: новый приглашённый аккаунт открывает RU/KK из браузера, видит только свой тестовый проект; другой аккаунт и неавторизованный запрос получают отказ. Вход → согласованное предложение → договор → DOCX/PDF; оригинал не выдаётся по прямому URL. Перезапуск только новой службы сохраняет состояние. Лишь после этого выдавать ссылку.

## Откат

1. До миграции сделать проверенную копию демобазы, приватных файлов, ссылки на текущий релиз и его отдельного конфига. Для согласованности снимка остановить запись в демо или использовать штатный SQLite backup и согласованный снимок файлов. Проверить восстановление отдельно; секрет и документы не помещать в Git.
2. При сбое прекратить доступ только к демохосту и остановить только его службу. Сохранить копию неудачного состояния для диагностики. Вернуть указатель на прошлый релиз; если предыдущая версия несовместима с новой схемой, восстановить согласованный предрелизный снимок **только демоданных**. Не обнулять и не возвращать назад денежный журнал с уже учтёнными запросами. Если это первый запуск, удалить только собственное подключение virtual host, не глобальные настройки.
3. Повторить `nginx -t`, согласованный reload, проверки действующих сайтов и демо. Не заявлять откат проверенным на GRACE без его фактической репетиции.

**Для ссылки заказчику осталось:** подставить утверждённый поддомен на GRACE, получить SSL и выполнить проверки хоста, отдельных ресурсов и настроек, после чего проверить ссылку извне. Этот материал не подтверждает выкладку или доступность домена. Никакие сервисы GRACE не менялись.

## Файлы и порядок для владельца

- Взять только проверенный commit из отдельной ветки, не main. В новом отдельном релизе `/opt/eseptep-pilot/releases/<COMMIT>` подготовить Python 3.12 и собственную `.venv`, установить `pip install -r requirements-hosted-pilot.txt` и выполнить `pip check`. Отдельный пользователь и закрытый localhost, `/var/lib/eseptep-pilot` с закрытыми правами; никакой общей базы, каталогов или socket GRACE. Никаких клиентских данных при подготовке.
- Скопировать `ops/closed-pilot.env.example` в отдельный root-owned env-файл с правами 0600. Вписать вручную уникальный Django secret, точный hostname вместо placeholder и реальные закрытые пути. Оставить ИИ выключенным. Создать отдельный системный unit и virtual host по `ops/eseptep-pilot.service.example` и `ops/eseptep-pilot.nginx.example`, проверить порт и сертификат. Не изменять текущий виртуальный хост GRACE.
- От имени выделенной службы с тем же EnvironmentFile и working directory запустить `python manage.py check --deploy`, `python manage.py migrate --plan`, затем одобренную миграцию только новой базы и `python manage.py collectstatic --noinput`. Для одиночных команд можно использовать transient systemd unit с теми же EnvironmentFile, User, Group и WorkingDirectory; не печатать окружение и не передавать ключ в argv. Отдельный администратор и раздельные клиент/магазин; добавить каждому допущенному группу `ESEPTEP closed pilot`. Для демонстрации предложений задать `ESEPTEP_PILOT_SUPPLIER_USERNAME` на приглашённый активный профиль магазина. Создать разрешённый пилотный город и включить только нужные тестовые проекты. Шаблоны автоматически мигрируют как черновики; пользователь может создавать договоры без ИИ. Для персонального допуска к платным операциям позже нужна также группа `ESEPTEP paid pilot`.
- Перед подключением DNS и прокси проверить только свой unit, затем `nginx -t`. Протестировать отказ регистрации/чужому проекту/прямому media, вход в одном адресе, расчёт вручную без платного ключа, отдельный ответ магазина, «Мой ремонт», договор, Word/PDF и повторное открытие. Испытать откат в изолированной копии и проверить отсутствие изменения портала GRACE до передачи адреса.

### Безопасный перенос денежного журнала (позже, только после разрешения)

Один журнал для планов и договоров с общим потолком $10. До любых действий остановить или отключить все локальные платные пути. Провести приватную проверку счётчиков сведений, размера резерва и штата; нерешённые резервы не удалять и не считать сэкономленными. Создать согласованную копию исходной SQLite средствами SQLite backup API после выключения записей (не простой copy работающей базы/WAL). Проверить integrity_check, счётчики `accounted_cents`, `open_holds`, лимит и SHA-256 у снимка; перенести snapshot по уже согласованному защищённому доступу в закрытую директорию, сверить SHA и счётчики, назначить права службе, переименовать в конечный путь без затирания существующего журнала. Данные журнала и ключ не отправлять в чат, в Git или HTTP. Старый экземпляр оставить выключенным для платных функций. Не создавать новый журнал, не копировать ключ из локального .env, не увеличивать потолок и не откатывать журнал при откате кода. При недостатке полного резерва обе платные кнопки оставить отключёнными; разрешённые операции без ИИ работают. После отдельного разрешения задать серверный ключ в EnvironmentFile и необходимые flags; старт не должен делать сетевого вызова.
